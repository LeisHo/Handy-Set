extreme cursor tilt/distance. so i dont understand why we need that?"
Read Handy Dandies' own real `updateCursorTarget()` (main.js ~1934) --
it raycasts the actual cursor position through the camera onto a
world-space plane, no normalized-magnitude abstraction anywhere.
HANDYSET's own `tiltMagnitude` (dividing screen distance from center by
half the smaller screen dimension) needed a near-screen-edge cursor
position before the signal approached its max -- that mismatch, not a
math bug, was why tracking looked like it needed extreme values.

Ported Handy Dandies' raycaster approach for the MOUSE path only --
device-orientation input keeps the normalized magnitude/angle circular
offset, the correct abstraction for a physical tilt angle with no
on-screen position to raycast from. Required one adaptation beyond a
literal port: HANDYSET's single hand sits at world origin, but its own
saved camera is framed/aimed at a completely different point (roughly
y=33, matching the model's visible geometry after scale/pivot, not the
hand's own logical anchor) -- a literal absolute raycast hit produced
wildly wrong, near-vertical rotations even for a dead-center cursor.
Fixed by using the OFFSET from a screen-center raycast (screen center =
zero offset = neutral gaze) instead of the raw absolute hit.

Found and fixed 2 further issues during live verification:

1. `tiltMagnitude`/`tiltAngle` still needed to update for mouse input in
   parallel with the new raycast -- Reactive Arm Length/Responsive Wrist
   Splay read them directly, not the new `cursorNDC`/`tiltTarget`. An
   initial cut removed them entirely (reasoning they were now redundant),
   silently freezing both reactive systems at their startup value the
   instant mouse input took over.

2. The REAL cause of the hand going fully invisible -- both this
   session's own earlier "extreme combined rotation" finding (flagged as
   unresolved) AND a new regression this exact round, where the hand
   started vanishing at completely ORDINARY cursor positions once
   tracking became proportionate: three.js's default frustum culling uses
   `geometry.boundingSphere`, computed once from raw UNSKINNED bind-pose
   vertex data -- it never accounts for skin/bone deformation. Confirmed
   directly via an independent `WebGLRenderer` instance (bypassing this
   app's own composer/outline pipeline entirely, ruling out any composer-
   specific cause): 0 triangles drawn with `frustumCulled` left at its
   `true` default, 15,046 triangles drawn with it forced `false`, same
   scene/camera/pose, nothing else changed. Fixed by disabling frustum
   culling unconditionally at hand creation -- cheap and safe at this
   project's own small hand-count scale. This also retroactively explains
   an EARLIER session's own "hand vanished at offset=179, widening FOV to
   90 brought it back" observation, previously misdiagnosed as "the roll
   axis is just hard to see in general" -- it was really this same
   culling bug, reachable at any sufficiently-rotated pose.

Live-verified across several cursor positions (dead center, modest
offsets in multiple directions, a larger-but-not-extreme offset): stable,
visible, proportionate response every time, no vanishing, wrist crop
still correctly scoped (confirmed still on and not over-cropping

Compared live `window.__debug.cfg` between the two URLs and found 2 real

`wristSplayResponsiveEnabled` (`false` under `?dev=1` vs the raw

key was present in either tab) — the divergence was structural.

Root cause: `loadRemoteSettingsOnStartup()` (main.js) fetches the
git-tracked Sync settings and calls devPanel.js's own
`applyFullDevPanelState()`, which writes each saved value via
`document.getElementById(id)` + a real `input`/`change` event dispatch —
`applyControlValues()`'s own `if (!el) return` makes a missing DOM
element a silent no-op. devPanel.js's `initDevPanelEngine()` only builds
that DOM eagerly when `isDevAllowed` (`if (isDevAllowed)
ensureDevPanelBuilt();`) — the panel's VISIBILITY gate, by
TEMPLATE_DEV_PANEL.html's own design. On a plain production visit (no
`?dev=1`, not localhost) that DOM never existed at all, so the entire
remote-settings apply silently did nothing on every control — every
ordinary visitor saw the raw hardcoded literal defaults in main.js, not
the tuned values actually saved via Sync/Set-as-Default. Confirmed via
direct `.parent`-chain-style DOM checks: `slidermodelRotY` and every
other dynamic control were absent from the DOM in the non-dev tab
(`sliderExists: false`), only the 2 built-in static Dev Panel/Debug
`.dev-section` shells from index.html's own raw markup were present.

Fixed in `loadRemoteSettingsOnStartup()` (main.js only — devPanel.js
kept as the verbatim template copy, per this project's own convention):
call `window.ensureDevPanelBuilt()` unconditionally right before
`applyFullDevPanelState()` runs. Safe because `ensureDevPanelBuilt()` is
already idempotent (`if (devPanelBuilt) return;`) and the panel's own
*visibility* is a separate, pure-CSS `.dev-mode` gate this change never
touches — a normal visitor still never sees a DEV button or panel, they
just now get the DOM built silently in the background so the remote
settings have something real to write into. Live-verified: after the
fix, `cfg.bgColor`/`wristSplayResponsiveEnabled`/every other field
checked read byte-identical between a fresh `?dev=1` load and a fresh
plain load, and a screenshot of the plain URL confirmed the panel/DEV
button both stay invisible as before.
